### Why it works this way

ArkType's `@ark/schema/out/kinds.js` runs `$ark.resolvedConfig = mergeConfigs($ark.defaultConfig, $ark.config)` the moment the module is evaluated. The domain node's `applyConfig` hook runs **once at type parse/compile time** and reads `$.resolvedConfig` to decide whether to bake in `numberAllowsNaN: true`.

- **`index.ts`**: `arktype/config` is evaluated first → `configure()` sets `$ark.config.numberAllowsNaN = true` → when `kinds.js` later resolves `$ark.resolvedConfig` and `schema.ts` compiles `Point`, `numberAllowsNaN` is already present → NaN is allowed.
- **`broken.ts`**: `arktype` (and therefore `kinds.js`) is evaluated before `config.ts` → `$ark.resolvedConfig` is frozen with default values → `Point` is compiled without `numberAllowsNaN` → calling `configure()` afterwards cannot retroactively recompile already-parsed nodes → NaN is rejected.

In ESM, static `import` declarations are evaluated depth-first in declaration order, so the source ordering of `import` lines directly controls which module's side effects run first.
